# 规格问题清单

实现过程中在 `02-后端开发规格书 v2.0`、`03-接口契约 v1.0`、`01-PRD v0.1` 之间发现的
不一致与缺陷。**每条都附实测数据**，不靠推理。

分两类：
- **A 类：已按实测修正并写进代码**（有明确技术判据，属于实现层面必须做的修正）
- **B 类：未自行修改，需文档作者决策**（涉及产品承诺 / 数值手感 / 命名，不能由实现方单方面定）

---

## A 类：已修正（代码即实测依据）

### A1. D5 的 τ 搜索范围导致"自信地报错八度"

**规格原文**：`τ 范围 [floor(sr/660), ceil(sr/90)]`，即搜索区间上限被压到 660Hz。

**实测**：

| 输入 | 规格范围下的输出 | 真实值 | 偏差 |
| --- | --- | --- | --- |
| C6 (1046.5Hz) | C5 (523.4Hz) | C6 | **1200 音分** |
| A5 (880Hz) | A4 (440.1Hz) | A5 | **1200 音分** |
| F#6 (1500Hz) | B4 (500.1Hz) | F#6 | **1902 音分** |

置信度全部 `conf ≈ 1.0`。**这些错值落在音域内，靠"音域过滤"查不出来**——前端会拿到一个
看起来完全可信的错数字，实时音块会直接骗人（D11 是全项目最不能出错的通道）。

**根因**：真实周期短于 τMin 时基频凹陷不在搜索区间内，YIN 会落到 2 倍 / 3 倍周期上。
实测证明：**全范围搜索（τ 从 1 起）时每个频率都精确落在真实周期上**。

**修正**（`game/js/core/pitch.js`）：搜索从 τ=1 起；"超范围"改由**出口的音域过滤**拒绝
（返回无音高），而不是靠限制搜索区间。修正后精度反而提升：

| 指标 | 修正前 | 修正后 |
| --- | --- | --- |
| 纯正弦最大误差 | 0.69 音分 | **0.13 音分** |
| 单帧耗时 | 1.04ms | **0.96ms** |
| 超范围错值泄漏 | 4/4 | **0/4** |

### A2. D5 的 CMND 累加起点错误，使 τMin 处恒为 1.0

**规格原文**：差分函数 `for (tau = tauMin; tau <= tauMax; tau++)`，CMND 累加
`for (tau = tauMin; ...) running += yin[tau]`。

**实测**：`yin[tauMin]` 对**任何信号**都是 `1.00000`。因为第一次循环时 `running` 恰等于
`yin[tauMin]` 本身，`yin * 1 / running = 1`。这既丢失 CMND 的物理意义，也让任何基于
τMin 的判据失效（排查 A1 时，我先后加的两道闸门都是被它废掉的）。

**修正**：按 YIN 论文定义，累加覆盖 `τ = 1..tauMax`，比较长度统一为 `W - tauMax`。
修正后音域内信号的 CMND ≤ 0.0014（阈值 0.15，余量极大）。

### A3. `Date.now()` 用于回合计时，容器节流下会失真

**规格原文**：D3 的"静默 3s 中止""RECORD 最长 6s"、D3 的"COUNTDOWN 采集 500ms 基线"。

**问题**：这些判定全部用挂钟时间。容器里 `setTimeout` 有节流、可能跑得比真实时间慢，
会让校准被拖长；设备改时间更会让判定直接错乱。

**修正**：改用 `performance.now()`（单调时钟）；噪音校準改为**固定采样次数**（12 × 40ms）
而非挂钟判定。

> 这一条是排查集成测试时先踩到的：校准循环在虚拟时钟下变成无限循环，暴露了它对挂钟的隐式依赖。

### A4. D2 的加载顺序与 D8 的 PRNG 依赖自相矛盾

**规格原文**：D2 加载顺序把 `melody.js` 排在 `fleet.js` **之前**；
D8 要求 melody 用种子 PRNG，而 D9.2 把 `mulberry32` 写在 `fleet.js` 名下。

**结果**：`melody.js` 加载时 `Siren.Fleet` 还不存在。`tools/selfcheck.mjs` 的依赖检查直接拦下。

**修正**：把 `mulberry32` 提到**最先加载且被双方共同依赖**的 `pitch.js`；
`fleet.js` 与 `melody.js` 都从那里取。**加载顺序按 D2 原文不动。**

### A5. D7.2 的移调补偿实现会击穿 P2 承诺

**规格原文**：D7.2 示例只返回折叠后夹到 ±2 的 median；示例注释写"整体低八度 → 完全不扣分"。

**实测**：按示例实现，**低八度演唱只得 65 分**（`offset=0` → 期望频率差 1200 音分 →
Pitch 维度 0 分）。P2「相对音高不惩罚」直接失效。

**修正**（`score.js`）：把移调拆成两部分——
- `octaveShift`：整八度差异，**完全补偿**（这才是"低八度不扣分"的实现）
- `fineOffset`：±2 半音内的整体跑调补偿，超出部分如实计入 Pitch

修正后：低八度 / 高八度 / 整体 ±2 半音 **全部 100 分**；整体跑 5 个半音 → 补偿 2 个 →
剩 300 音分如实扣分 → 65 分（正是 D7.2 想要的行为）。

### A6. DTW 对齐未使用移调补偿，导致整体跑调被判"全漏唱"

**实测**：整体跑 2 个半音时，每个音代价约 200 音分、刚好越过命中阈值，
**7 个音全被判成漏唱**（completeness 归零、总分 30）。

**修正**：对齐的代价函数**先扣掉整体移调补偿**再比音高——对齐要回答的是
"哪个音对应哪个音"，不是"唱得准不准"。移调量用穷举搜索（[-12,+12] 半音中使对齐代价最小者），
比"rawMedian 推八度"稳健（后者在整体跑 5 个半音时会推成 0 个八度）。

### A7. 原创旋律生成器的"连续同方向"约束有边界漏洞

**规格原文**：D8「不得连续 3 个同方向进行」。

**实测**：`[2,-1,-2,-5]` 这类**末音收尾**构成的连续下行会漏过检查——末音
（`degree % 5 === 0` 的主音）走的是不受方向检查约束的独立分支。

**修正**：改为"整句生成 + 统一校验 + 拒绝重采样"（最多 200 次，仍失败用保底旋律）。
300 个种子扫描：**零违规**。

### A8. D8 的五声音阶与"耳熟能详"直接冲突

**规格原文**：D8 给的熟曲示例 `degrees` 是五声音阶（0/2/4/7/9 = C D E G A）。

**问题**：中文最耳熟能详的公版童谣基本都不是五声音阶——《小星星》含 F(3) 和 B(6)、
《两只老虎》含 F(3)。硬套五声音阶折算会把旋律改到"听不出来"，**直接毁掉 D8 想要的特性**。

**修正**：熟曲库改用 `scale: 'major'`（自然大调级数），**原创旋律仍严格用五声音阶**。
对 P2（相对音高、移调补偿）无影响——两者都与音阶无关。

### A9. D6 的音符合并规则缺时间判据，连续同音被吞

**规格原文**：D6「音符边界：相邻稳定段音高差 ≥ 80 音分 → 新音符；< 80 → 合并」。

**实测**（`tools/test-hum.mjs`，端到端音频链路）：

《小星星》第 1 句是 7 个音，其中开头有两个 C、中间两个 G、两个 A。帧序列完全正确——
两个 C 之间确实有一帧静音（D4.3 强制的 40ms 音符间隔造成的），切分器也确实把它切成了**两段**。
但紧接着的合并步骤**又把它们并回一个音**，因为两段的音高差是 0（< 80 音分）。

结果：端到端只能切出 **4/7** 个音，完整度 57%、音型轮廓 50%，总分被压到 62。

**根因**：合并规则只写了音高判据。合并的本意是抗"同一个音内部的抖动"，
但静音是**明确的换音信号**，不应该跨越它合并。

**修正**（`game/js/core/segment.js`）：加时间判据 ——
只有两段间隔 ≤ 25ms（小于半帧）才允许合并；被静音分开的两段一律不合并。
修正后端到端 7/7，真唱与哼唱均得 98 分。

> 这个缺陷**单元测试查不出来**（`test-score.mjs` 直接喂理想音符，跳过了切分），
> 只有走完整音频链路的端到端测试才能暴露。属于"必须建 test-hum.mjs 才能发现"的一类。

### A10. 移调补偿绕过了 D7.2 的 ±2 半音上限

**规格原文**：D7.2「补偿上限 ±2 半音：超出部分不补偿，作为真实跑调计入 Pitch」，
示例注释写"玩家整体跑 5 个半音 → 只补偿 2 个 → 剩下 300 音分如实扣分"。

**实测**：整体跑 3 个半音仍得 86 分（Pitch 维度 67%），5 个半音也偏高。

**根因**：修 A6（对齐未用移调补偿）时，我让补偿量直接取了
"使对齐代价最小的 shift"（搜索范围 ±12），**把 ±2 这个产品上限绕过去了**。
对齐用的 shift 和给玩家补偿的量是**两件事**，前者可到 ±12，后者必须夹在 ±2。

**修正**（`score.js` 的 `computeTransposition`）：拆成
- `octaveShift` —— 整八度差异，完全补偿（P2「低八度不扣分」靠它）
- `fineOffset` —— 夹在 ±2 半音内的细调补偿，超出部分不补，留给 Pitch 维度如实扣分

修正后：低八度/高八度/±2 半音全部 100 分；整体跑 5 个半音 → offset=2、剩 300 音分 → 65 分，
与 D7.2 示例完全一致。

### A11. 输入电平偏低的设备会静默失败（无任何提示）

**发现方式**：真机试唱（`game/js/lab/lab.html`）。用户报告"我一直在唱，却总是显示录到静默"。
采集统计显示：120 帧里 **100 帧电平低于 0.005**，平均 0.00125，峰值 0.032 RMS（约 −30 dBFS）。
**正常笔记本麦克风贴着一拳距离唱歌应有 −12 ~ −6 dBFS，差 15–20 dB。**

**根因**：差距来自设备/系统层（其他程序共享麦克风、系统输入级别、内置麦增益偏低），
用户无法自行解决。而**代码把"信号太弱"和"用户没唱"当成同一件事**——
两者都表现为"无音高帧"，于是玩家唱了满场却拿 0 分，且得不到任何解释。

**离线验证**（带共振峰的人声模型，复现"高音时基频弱于泛音"）：
YIN 在 **0.003 RMS 以上就有 100% 检出率**，5 个音高 × 6 档电平全绿。
→ 所以检测器不是瓶颈，**瓶颈是信号没被抬进可用区间**。

**修正**（`game/js/core/audio.js` + `game.js`）：
- 新增 `computeInputGain(peakRms, noiseRms)` / `applyInputGain(buf, gain)`
- 增益策略**宁可少放大**：已够响则完全不动（1x）；上限 8 倍；
  不允许把底噪抬到 0.02 以上（否则噪声会被判成音高）；绝不削波
- `game.js` 在**每句录完后**用该句实测峰值更新增益，供下一句使用
  （开场 LISTEN/COUNTDOWN 时玩家还没出声，测不到峰值，所以第一句用 1x）
- 电平统计始终用**原始**缓冲，增益只作用于检测副本——否则再也看不出设备真实电平
- 输入过轻时广播 `LOW_CONFIDENCE`（复用契约 C4 已有码，前端文案"有点听不清，再靠近一点"恰好对应），
  **未擅自新增状态码**——C4 表是封闭的

**未做**（待契约维护者决定）：建议给 `attempt:pitch` 载荷加一个 `level` 字段（原始 RMS），
让前端能直接显示电平条引导用户。契约 C3 的载荷定义是封闭的 5 个字段，故未擅自扩展。

> 附带教训：增益归一化最初只做在开发工具（lab）里，**正式路径 `game.js` 没同步**。
> 两个入口共用同一套采音逻辑时，改动必须同时落到两处，否则"工具里好了、游戏里没好"。

### A12. 首次录音时没有任何"该开口了"的信号

**发现方式**：同一轮真机试唱。用户报告"录到的声音很短，但我一直在唱"。

**根因**：点「开录」后直接进入采集，而 3 秒无音高就中止。
用户还在看屏幕、准备开口，就被判成静默结束——**录音时长 5615ms，实际只覆盖前 2.6 秒**。

**修正**（`game/js/lab/lab.js`）：加 3-2-1 倒数（与 `game.js` 的 COUNTDOWN 阶段一致）；
静默宽限期从 0.8s 提到 1.5s；无音高时实时显示"静默 Ns 后结束"，让用户看到系统在等。
**正式游戏本就有 COUNTDOWN 阶段，故 `game.js` 不受此缺陷影响。**

### A13. `MIC_DENIED` 的 level 与契约不符、`MIC_RETRY` 从未广播

**发现方式**：写前端速查卡时逐条核对契约 C4 状态码表与实现，发现两处偏离。

**问题 1 —— level 不符**：契约 C4 把 `MIC_DENIED` 定为 **error** 级
（前端文案"如果您拒绝了麦克风权限，游戏就听不到您的声音咯"），
但实现里 `getUserMedia` 被拒时发的是 `notice('MIC_DENIED')`。
**后果**：前端若按契约监听 `Siren.on('error', ...)` 来处理权限引导，**永远收不到通知**，
用户拒权后会静默进入兜底模式，而前端不知道要提示什么。

**问题 2 —— 定义了但从未发出**：契约 C4 定义了 `MIC_RETRY`
（notice，"再点一下让她开口"，用于权限被系统重置或切后台回来），
但实现里**没有任何一处广播它**，该码是死的。

**修正**（`game.js`）：拒权路径改为 `error('MIC_DENIED', ...)` + `notice('MIC_RETRY')`，
并在集成测试中加两条断言钉住（含 level 校验）。

> 附带教训：这两处都属于"契约与实现对不上，但两边单独看都没问题"。
> 只有把契约表**逐行**跟实现对照才会发现——静态检查（selfcheck）查的是代码规范，
> 查不出语义偏离。已在 `test-integration.mjs` 里为两个码各加断言。

## B 类：未自行修改，需文档作者决策

### B1. 船队模型与"期望触礁数 = 分数"不符 —— ✅ 已决策并修复（2026-09）

**规格原文**：D9.3「长期期望严格等于分数」。

**当时实算**（旧模型 `pull > THRESHOLD_T`，`LURE_GAIN=1.5 / THRESHOLD_T=0.8`，
`k ~ 截断正态(1.0, 0.24)`，下界 0.35），解析解与 1000 局模拟一致（偏差 ≤ 0.22 条）：

| 每句分 | 一局总船数 | 与"= 分数"的差 |
| --- | --- | --- |
| 10 | 0.0 | −10 |
| 20 | 0.0 | −20 |
| 30 | 0.1 | −29.9 |
| 40 | 8.2 | −31.8 |
| 50 | 39.2 | −10.8 |
| 60 | 67.8 | +7.8 |
| 70 | 84.2 | +14.2 |
| 80 | 92.2 | +12.2 |
| 90 | 95.8 | +5.8 |
| 100 | 97.7 | −2.3 |

**问题**：实际是 S 形曲线。分数 20 完全引不来船，分数 40 只有 8 条；而 PRD §12 的
守门指标是"回合 1 ≥65 分"——新手落在 20–40 分段时画面上不会有船进来，
"船越多越好"的即时反馈在这一段是断的，而那正是首次体验最关键的一波。

**决策**：**改为线性映射。** 产品负责人要求：
1. `k` 分布改为**有界**（下界 0、上界 1）
2. 保证 **0 分时一条船也不触礁**（下界 k 的船也能逃脱）
3. 保证 **100 分时触礁率 100%**（上界 k 的船也不能逃脱）

**实现**（`game/js/core/fleet.js`）：

```
k ~ Uniform(0,1)（有界）
触礁条件：k < score/100        ← 注意是严格小于
```

用严格小于而非 `<=`，两个端点才是**构造保证**而非概率保证：
- `S=0`：`k` 取自 `(0,1)` 开区间、取不到 0 → `k < 0` 恒不成立 → 必然 0 条
- `S=100`：`k < 1` 恒成立 → 必然 100 条

**数学性质**：单条船触礁概率**恰好等于 score/100**，于是
**D9.3「长期期望严格等于分数」现在精确成立**（11/11 分数段偏差 < 1 条）。
单局波动服从二项分布 `B(100, score/100)`，σ 在 50 分处为 5.0，与 D9.3 说的
"1σ ≈ ±4.4 条"量级一致。

**连带改动**：
- 旧参数 `THRESHOLD_T` / `LURE_GAIN` / `K_MEAN` / `K_SIGMA` **全部作废并删除**
  （`K_MIN` 语义变为 k 的下界 0，新增 `K_MAX = 1`）。**D9.1 的 CONFIG 与 D12 的调参表需同步修订。**
- 不再有"全局增益"这个旋钮——再引入它会重新打破"触礁率 = 分数"。调难度请改判定曲线本身。
- 手感变化：船与船的抗性差异从"正态分布、中间抗性居多"变为"均匀分布、各抗性等概率"。
  极端抗性的船比例更高（特别容易勾的和特别难勾的都更多）。
- 曲线不再有 S 形拐点，40–60 分段的"进步感"更线性，少了一点"过坎突然起势"的爽感。

### B2. D13 的"分数 100 → 触礁数 = 100"在旧公式下不可能 —— ✅ 已随之修复

**旧模型实测**：分数 100 时 `pull = 1.5k`，需 `k > 0.533` 才触礁；而 `k` 有约 2.3%
落在 0.35–0.533。1000 局实测**均值 97.7、最小 93，只有 9.8% 的局能到 100 条**。
后果是**玩家唱到满分也拿不到 100 条船**，结局 A（要求恰好 100 条）几乎不可达。

**根因（重要）**：这不是参数没调好，而是**判定形式本身的限制**——
只要判定式是 `pull > T`，`k → 0⁺` 时 `pull → 0`，永远够不到正数阈值，
所以"满分必全触礁"在数学上不可能实现；而把 `T` 降到 0 会让**任何正分数都全触礁**
（1 分也 100 条），曲线彻底塌掉。

**修复**：随 B1 一起换成 `k < score/100`。现在 1000 局**最小 = 最大 = 100**，
满分会稳定触发结局 A。

### B3. PRD 与规格书三处直接冲突 —— ✅ 已决策（2026-09）

PRD 是 v0.1 待评审，规格书是 v2.0 唯一依据。**决策：三处全部按规格书执行**（与当前实现一致）：

| 项 | PRD 说 | 规格书说 | **决策** |
| --- | --- | --- | --- |
| 诊断话术 | §6.2 **必须**给"第 3 个音低了，再高一点点" | D7.4 **强制删除**，接口不得返回维度值 | **按规格书** → 接口只返回 `{ score }` |
| 回合数 | §5.2 "N=1..3"、§7.1 "3 回合" | D9.1 `PHRASES: 5`、音数 3/4/5/6/7 | **按规格书** → 5 回合 |
| 打分维度 | §6.1 三维 | 四维 30/35/25/10 | **按规格书** → 四维 |

关于 PRD §7 的"拉力/船距 tug-of-war"模型（`Δd = -score_norm × 22 × lure × ...`、
结局 A=触礁 / B=船逃脱）与规格书 D9 的"船队模型"（每波 20 条、触礁数即分数、结局 A/B/C/D）：
**决策：以船队模型为准，PRD §7.1 的位移公式作废。**
理由：§7.1 表格里那段"（加入船只数量的机制…）"是后加的插入痕迹，船队模型是更新的一版；
且 PRD §8.1 已注明"最终评分以吸引的船只数量展示"。
**PRD §7.2「结局的两种叙事」仍然有效**——只是结局从 2 种扩为 A/B/C/D 四种，文案需前端相应扩展。

> 附：船队模型的数值参数已于 B1 决策中从 S 形改为线性映射，
> 因此 PRD §7.4 的数值表**需要按线性重做**（这正是当初把 B1 标记为"会让数值表作废"的原因）。
